Building a live fleet-tracking and route-optimization platform from scratch

At the facility where I work as an automation engineer, vehicles go out every day to collect material from dozens of locations around the city. Routes were being planned by intuition, nobody knew where a vehicle actually was at any given moment, and the people waiting for a pickup had no idea when it would arrive. It was a classic logistics problem — and a great excuse to build real software.

The result is a platform that is now part of daily operations: managers create collection jobs, the system builds a traffic-aware route, every vehicle is tracked live on one map, and each location automatically gets an SMS when the vehicle departs and again shortly before it arrives. Here is a tour of the interesting engineering decisions.

A routing engine that refuses to die

The heart of the system is the routing engine. I wanted real road geometry and live traffic, but I also wanted the platform to survive quota limits and provider outages — a lesson that comes straight from industrial automation, where a single point of failure is never acceptable. So routing runs through a fallback chain:

  1. TomTom — primary provider, with live traffic data and delay estimates;
  2. OpenRouteService — second in line;
  3. OSRM — public routing without traffic;
  4. Haversine estimate — the mathematical last resort, so the app always answers.

A daily quota guard sits in front of the primary provider: when usage approaches the free-tier limit, the chain silently degrades to the next engine instead of failing. Stop ordering uses a nearest-neighbour heuristic over a real road-distance matrix, and the system can generate one to three alternative routes — like a navigation app — so the planner picks the trade-off between fastest and shortest.

Live tracking without losing your mind

Drivers share their position from a phone; the backend fans it out over WebSocket to every open map. Two details mattered far more than the happy path:

  • Deviation detection. If consecutive GPS pings land far off the planned geometry, the server automatically re-routes from the vehicle's actual position — rate-limited so a GPS glitch doesn't trigger a re-route storm.
  • Map rendering discipline. The naive approach — redraw everything on every ping — makes the map flicker and the camera jump. The final version updates line layers only when geometry actually changes, moves markers instead of recreating them, and refits the camera only when the set of visible data changes. Smooth, boring, correct.

The SMS choreography

Each stop gets two messages: one when the vehicle departs, and one roughly thirty minutes before arrival — computed from the live ETA, not a fixed schedule — containing a one-time delivery code. The driver confirms the code on site and records what was collected, which feeds a live fill-rate calculation for the vehicle. Departure is idempotent: pressing the button twice never double-sends messages. In development, the whole SMS pipeline runs in simulation mode and writes to a log table instead of sending — so the full flow is testable end to end without a single real message.

What automation engineering taught me about software

Building PLC systems changes how you write web software. Three habits carried over directly:

  • Assume the field is hostile. Sensors fail, networks drop, users double-press buttons. Every critical endpoint is wrapped so one bad request — a foreign-key violation, a malformed ping — can never take the whole server down.
  • State machines beat flags. Jobs and stops move through explicit states (planned → en route → arrived → collected), exactly like a machine sequence. Debugging becomes reading a state, not divining a combination of booleans.
  • Simulate before you commission. The platform includes a full driving simulator that replays a route with realistic timing, fires the same API calls a real phone would, and triggers the same SMS logic. We "commissioned" the software the way you commission a machine — in simulation first.

The stack

React + TypeScript + Vite on the front end, installable as a PWA so drivers use it like a native app. MapLibre GL with OpenStreetMap tiles for the map. Node.js + Express + Prisma on the back end, with WebSocket for live data, JWT-based roles (admin / manager / driver), and automatic monthly report archiving. Nothing exotic — the value is in how the pieces are wired for resilience.
